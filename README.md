# MedicalDiscImporter

Windows 11 ARM64 / x64向け .NET 10 / C# / WinForms光学ディスク取り込みアプリ。
M1に続く **Defender検査・結果詳細・DICOM一覧・RSBase自動取込用出力** を実装。施設での受入試験は未完了。まずダミーデータで評価する。

## 今回の機能

以下は3つの処理をすべてONにした既定動作。取込操作エリアでISOイメージ・ウイルススキャン・DICOM送信を個別に選択できる。

- ディスクの全ファイルをアクセス制限されたローカルNTFSへコピーし、IMAPI2FSでUDFの再構築ISOを作る。
- ISOを読み取り専用マウントし、元ファイルのパス・サイズ・SHA-256とフォルダ構成を照合。必ず解除を確認する。
- コピーした**全ファイル**をDefenderのカスタム検査にかける。ISO本体だけの検査で代替しない。
- 検査前後の通常稼働・リアルタイム保護・定義日時を確認する。終了コード0だけでは合格にしない。
- 対象フォルダの開始イベント1000と同じScan IDの完了イベント1001、検出履歴、期間中の検出・中止・エラー・設定変更を確認する。修復済み検出も出力禁止。
- 検査後に全ファイルとISOを再照合し、削除・修復・変更を検知する。
- fo-dicom 5.2.6で全ファイルを拡張子に依存せず解析し、患者名・撮影日・シリーズ番号・シーケンス・ファイル数をシリーズ単位でメインフォームに一覧表示する。
- シーケンスはSeriesDescription、SequenceName、ProtocolNameの重複しない値を併記。画像デコード・画像表示はしない。
- 撮影日はStudyDate → SeriesDate → AcquisitionDate → ContentDateの順。不明なら取り込み日で代用し、画面とjob.jsonに明示する。
- 合格後、ISOとRSBase用DICOMを指定先へ保存する（同じフォルダも指定可能）。DICOMは内容を変えずに `患者ID~000001~yyyy_MM_dd~検査名~RSB.dcm` へ改名し、取込先の直下へフラットに出力する。DICOMDIRや付属Viewerは出力から除外する。
- Defenderの検査対象ファイル数・重複しない脅威検出記録数・検査処理時間・定義バージョンを完了画面と記録へ表示する。取得不能な件数は0件と表示しない。
- コピー先のサイズ・SHA-256を照合後に最終名へ変更。上書き禁止。ISOとDICOMの成否を別々に記録し、部分成功を表示する。
- M1の二重起動・多重取り込み防止、数字キーパッド、進捗・中止、読取中スリープ抑止を維持。

## 受付画面

タイトルバーと画面内の見出しは「MedicalDiscImporter」。見出しを小さめにし、「患者IDとディスクを確認して、取り込みを開始してください」の案内は維持する。患者ID、光学ドライブ、取込操作を別々のエリアに分け、テンキーを枠なしのタイルにした。「更新」はドライブ右側、「設定」は画面右上に配置する。
USBドライブの接続・取り外し通知を受けて自動更新し、待機中は5秒ごとにもドライブとディスク状態を確認する。デバイス照会はバックグラウンドで行い、取り込み中は自動更新を止めて対象ドライブを固定する。認識できない場合は「更新」で再確認できる。
バーの代わりに「ディスク読込 → ISO作成・照合 → ウイルス検査 → ISO・DICOM出力」の工程を表示する。完了・処理中・未着手・停止・中止を文字と色で区別し、終了後も工程を残す。ISOの作成・照合と、検査合格後の最終保存は別工程。
結果は「DICOM一覧」と「保存先・検査の詳細」のタブで確認する。失敗・中止・DICOMなしの場合は詳細を自動で開く。患者IDが空欄・不正、またはディスク未認識の間は開始ボタンを無効にする。

### 取込オプション

| スイッチ | ON | OFF |
|---|---|---|
| ISOイメージ | ISOの作成・マウント照合・最終保存 | ISO作成・マウント・保存を省略。コピーした全ファイルを元の一覧と照合する |
| ウイルススキャン | サービスの接続確認とDefender検査。検出・不明・失敗は出力禁止 | サービスへ依頼せず、未検査として選択した出力を実行する |
| DICOM送信 | DICOM解析・一覧表示・RSBase用ファイルの送信 | DICOM解析・送信を省略し、取込先へ書き込まない |

初期状態は全ON。切り替え時に `settings.json` の `CreateIso`・`ScanForMalware`・`SendDicom` を保存し、次回起動で復元する。既存の設定に項目がなければ全ONを使う。スイッチ保存のために未設定の出力先を必須にしない。開始前にONの処理の出力先・定義鮮度設定・検査名だけを検証する。
取り込み中は切り替え不可。全OFFでは開始不可。スキャンだけ、ISOだけ、DICOMだけでも実行できる。
スキャンOFFは開始確認、待機・完了表示、scan.json／job.jsonで「未検査」を明示し、検査合格・検出0件として扱わない。スキャンONの失敗をOFFへ自動で切り替えることはない。ファイル内容・コピー先のハッシュ照合、パス制限、上書き禁止はOFFでも維持する。省略した工程は進捗上でOFFと表示する。

### バージョン

メインフォームのタイトルバーは `MedicalDiscImporter v20261107.1`。リリース番号は [Version.props](Version.props) の `ReleaseDate`（yyyyMMdd）で一元管理する。実行日の時計からは生成せず、本体のビルドに日付番号を埋め込む。同日中の別リリースは `ReleaseRevision` を1、2…と増やす（例：`v20261106.1`）。枝番0は表示を省略する。Windowsのファイル／アセンブリバージョンは `2026.11.7.1` の形式。

設定のサービス欄には、アプリ版と**稼働中のサービス自身が返した版**を表示する。サービス開始時・PID変更時・操作後に問い合わせ、表示中は通常30秒間隔で再取得する。「状態を更新」「接続を確認」では直ちに再取得できる。停止中や接続不能は未取得とし、ディスク上のEXEを稼働版とみなさない。
サービスの表示版は [ServiceRelease.cs](src/MedicalDiscImporter.Core/ServiceRelease.cs) の `Current`（初期値 **1**）で独立管理する。サービスの実装変更時だけ1、2…と増やし、本体の日付・枝番更新だけでは変更しない。古いサービス版は更新を案内し、同版は更新不要、新しい版もダウングレードを促さない。既存の `v20261106`・`v20261106.1` はサービス版1と同じ検査実装なので、旧表記を表示したまま互換版1として扱い、更新を要求しない。未知の日付版や情報なしは確認不能として更新案内する。サービスの停止や自動更新は行わない。新規導入・手動更新したサービスからは、日付ではなく `1` を返す。既存通信v2とJSONの任意フィールドは維持する。

## 使い方と出力

1. AutoPlayとAutoRunを施設の設定・管理ポリシーで無効化する。ディスク内Viewerを起動しない。
2. 設定画面でISO保存先とRSBase自動取込先（同じフォルダも指定可能）、およびDICOM検査名（既定 `CTMRI`）とISO検査名（既定 `CDROM`）を指定する。RSBase/RSDICOM側で監視しているフォルダを取込先に指定する。絶対パスのローカルフォルダ／UNC共有に対応。
3. Defender定義の有効日数を設定する（既定7日、1～30日）。設定は `%LOCALAPPDATA%/MedicalDiscImporter/settings.json` に保存。既存のDICOM出力先設定はRSBase自動取込先として引き継ぐため、アップデート時に確認する。
4. 患者ID（半角数字1～32桁）を入力し、ドライブと取込オプションを選んで開始する。確認画面には選択した出力先とスキャンのON/OFFを表示する。
5. 検査結果・一覧・保存先を確認する。失敗・中止・DICOMなし・部分成功を区別する。

ISOは `<ISO保存先>/12345~000001~2026_11_07~CDROM~RSB.iso` へ出力する。日付は取込開始時のローカル日付（完了日やDICOM撮影日ではない）。ISO専用の `IsoExamName` を設定に保存し、既存設定に項目がなければ `CDROM` を使用する。患者ID・取込日ごとに6桁の連番を永続記録し、監視側が取り込み後にファイルを移動しても番号を再利用しない。検査名を変更しても連番を継続する。ISO内容のサイズ・SHA-256照合後、準備領域から正式名へ変更する。元ISO・正式名・ハッシュ・状態の対応は `rsbase-iso-output.json` に記録する。
DICOMは `<RSBase自動取込先>/12345~000001~2026_11_05~CTMRI~RSB.dcm` の形式で出力する。区切りは各1個の `~`。検査名は1～40文字で、区切り・改行・ファイル名に使えない文字は不可。PatientID等のDICOMタグは変更しない。
DICOMの連番は入力患者ID・撮影日ごと。SeriesNumber、InstanceNumber、SOPInstanceUID、元パスの順で安定ソートし、6桁でゼロ埋め（100万以上は自然に桁を拡張）する。既存ファイルと永続採番記録の大きい方から続番を使い、同じ日付では検査名を変えても番号を戻さない。
同じ出力フォルダでは、ISOとDICOMで患者ID・日付ごとの連番を共有する。別フォルダではそれぞれで採番する。同一フォルダは許可するが、親子関係にある別フォルダは許可しない。
ISO保存先とDICOM取込先それぞれの `.MedicalDiscImporter/` は採番記録・排他ロック・非監視名の準備ファイル用であり、削除しない。複数PCはこの共有内のロックを使って採番し、RSBaseが直ちにファイルを消費しても番号を再利用しない。外部出力との衝突時にも上書きせず別番号を予約する。
全DICOMを準備領域へコピー・サイズ／SHA-256照合した後、1ファイルずつ正式なRSB名へ同じ共有内で変更する。複数ファイル全体の公開は原子的ではなく、監視側は途中から取り込む可能性がある。受け渡し済み件数は `job.json`、元ファイル・正式名・ハッシュ・状態の対応は隔離作業領域の `rsbase-output.json` に記録する。途中失敗で残った正式ファイルを削除・自動再送しない。
アプリの「受け渡し完了」はファイルを監視先へ配置したことを示し、RSBase内部の取り込み完了を確認する応答ではない。実RSBase/RSDICOM側で命名・監視・日付別採番が受理されるか、ダミーISO・DICOMで受入試験する。ISO拡張子の自動取込が有効かも実RSBase側で確認する。既存RSBase/RSDICOM自体は変更しない。

## Defenderの前提

この節の検査前提・出力禁止条件は「ウイルススキャンON」の場合に適用する。ユーザーが明示的にOFFにした処理は未検査として記録し、選択したISO保存・DICOM送信を行う。

Windows標準Windows PowerShell、Defenderモジュール、MpCmdRun、Defender Operationalイベントログを使用する。
完了表示の「検査対象」は実際に送って除外確認したファイル数であり、Defender内部の展開済みアーカイブ項目数ではない。「脅威検出記録」は検査期間中に照合した重複しないDetectionIDの件数（このPCの別の場所の検出も含め保守的に停止する）。検出イベントだけで件数を確定できない場合は件数取得不可と表示する。「検査処理時間」は除外確認・検査・結果確認を含み、ファイル転送やDICOM出力は含まない。`scan.json` と `job.json` に同じ値を保存する。
Microsoftの手順ではMpCmdRunは管理者実行が前提。除外設定・履歴を参照できる権限も必要。
**画面・取り込み処理は標準ユーザーで実行し、Defender処理は専用Windowsサービス（LocalSystem）へ依頼する。** 管理者パスワードは保存しない。施設ポリシーによる設定の非公開は回避せず、確認不能なら出力禁止を維持する。

### ウイルスチェックサービスの登録

設定フォームを開くと、Windowsのサービス管理情報から「登録状況」と「稼働状況」を自動で取得する。表示中は3秒ごと、および操作完了・管理者承認キャンセル後に再確認する。「状態を更新」でも再照会できる。状態の照会だけでは管理者承認やサービス操作を行わない。

| 状態 | 登録・更新 | 開始 | 停止 | 登録解除 | 接続確認 |
|---|---|---|---|---|---|
| 未登録 | 登録可 | 無効 | 無効 | 無効 | 無効 |
| 登録済み・停止中 | 更新可 | 有効 | 無効 | 有効 | 無効 |
| 登録済み・稼働中 | 更新可 | 無効 | 有効 | 有効 | 有効 |
| 開始中・停止処理中・削除待ち・状態取得失敗 | 無効 | 無効 | 無効 | 無効 | 無効 |

登録済みの場合はボタン名を「サービスを更新」に切り替える。確認中・操作中は各操作ボタンを無効にし、最後に取得した実状態に基づいて戻す。取得失敗を未登録とは扱わず、Windowsエラー番号も表示する。稼働状態とアプリとの通信結果は別表示で、稼働中だけでDefender検査合格とは扱わない。

1. 使用する端末向けの発行済みEXE（SurfaceはARM64、通常のIntel/AMD PCはx64）を配布用フォルダから起動する。
2. 「設定」→「ウイルスチェックサービス」で状態を確認し、未登録なら「サービスを登録」、更新時は「サービスを更新」を押す。
3. Windowsの管理者承認画面で承認する。標準ユーザーの場合は施設管理者が管理者資格情報を入力する。
4. 「登録済み・接続確認済み」と表示されたことを確認する。接続確認はDefender検査合格を意味しない。
5. 以後はアプリを標準ユーザーで起動する。サービスはPC起動時に自動起動する。

サービス名は `MedicalDiscImporter.Defender`。本体と検査用作業領域は `%ProgramFiles%/MedicalDiscImporter.ScanService/` に配置し、SYSTEMと管理者以外にはアクセスを許可しない。元の配布用フォルダは標準ユーザーが実行できる場所に置く。開発ビルドからのサービス登録は不可。
更新時は新しい配布用EXEから同じ「サービスを登録・更新」を実行する。停止・無効になっている登録も、自動起動へ設定して開始する。「サービス開始」「サービス停止」も設定画面から実行でき、管理者承認が必要。接続確認だけでは昇格やサービス設定変更は行わない。接続に失敗した場合はSCMの停止・開始中・実行中の状態とWindowsエラー番号も表示する。
解除ではサービスの停止とプロセス終了を待ってから登録の削除を要求し、保護された配置先のファイルは残す。Windowsの「サービス」管理画面などがハンドルを保持している間は削除保留となる場合がある。その状態で再登録するとWindowsエラー1072になるため、サービス管理画面を閉じてから再登録する。管理者操作を取り消した場合は操作しない。

ローカルの名前付きパイプでファイル内容とハッシュを転送する。サービスは任意コマンド・元ファイルのパス・出力先の指定を受け付けない。接続先のSYSTEM所有者、ローカル通信のアクセス権、相対パス、件数・容量を検証する。保護されたコピーを検査前後で照合し、アプリ側でも元データを再照合する。Defender設定の変更、除外の追加はしない。
接続確認・検査結果はアプリの受信確認を待ってからパイプを切断する。接続直後の切断や不正要求は1件の依頼の失敗として処理し、次の接続待機を継続する。通信方式をv2へ更新したため、旧EXEからの接続は不可。アプリとサービスを同じ配布版へ更新すること。サービスの診断ログは配置先の `service.log` に記録する（管理者のみ参照可能、最大約64 KiB、例外の型・コードのみで患者名・パスは記録しない）。
検査用コピーのため最大20 GiBの追加空き容量が必要。検査は端末ごとに1件ずつ受け付ける。検査中の別の依頼は接続待ちで失敗することがある。転送中断・サービス停止・タイムアウトは合格にせず、検査用コピーは後片付けする。異常終了で残ったコピーは次回サービス起動時に削除する。削除できない場合は正常動作を報告しない。
開発PC（x64）ではUAC承認を経た登録・起動、アプリの管理処理による停止・再開、解除・再登録に成功した。標準ユーザーからの接続は初回30回、再開後10回、再登録後10回の計50回成功し、自動起動設定と実行中状態を確認した。
後述の除外判定と完了イベント形式を修正後、標準ユーザーからサービス経由でダミーDICOMの実Defender検査合格と、合格後のダミー取り込みデータのISO・DICOM出力を確認した。194件の無害なダミーファイルも約7.5秒で検査合格した。終了コード0だけでなく、対象とScan IDを照合した開始1000・完了1001の証跡を確認している。Defender設定は変更していない。**PC再起動後の自動起動、ARM64実機・実ディスクでの受入は引き続き必要。**

検査前後に `MpCmdRun -CheckExclusion -Path` で実際の検査フォルダと全ファイルを確認する。終了コード1（除外対象外）のみ許可し、0（除外対象）やそれ以外のエラーは出力禁止とする。無関係なフォルダや拡張子の除外が設定されていても、対象全件が除外対象外と確認できれば検査を進める。プロセス除外はオンデマンド検査には適用されないため、存在だけでは停止しない。
ファイル・拡張子除外が非公開、条件付き除外の存在、脅威別アクション設定、アーカイブ検査無効・取得不能は引き続き合格にしない。理由は項目別に表示する。アプリはDefender設定を変更しない。
仕様根拠：[Microsoftの除外設定とCheckExclusionの終了コード](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-antivirus-exclusions-configure)。通常のカスタム検査を維持し、検出履歴やイベントの記録を省略するDisableRemediationは使用しない。
無効／受動モード、古い・未来日時の定義、権限不足、検査未完了、開始対象や完了イベントの相関不能、検出、履歴取得不能、検査後の変更、DICOM候補の破損では両出力を禁止する。
検査中の端末の別の場所の検出・設定変更も保守的に止める。
通常ファイルでDICOM解析不能なら対象外にするが、DICOMヘッダー／`.dcm`を持つ候補の破損は失敗扱い。
検査プロセスは30分でタイムアウト。中止・タイムアウトでも出力しない。中止後もOS側の検査が継続する可能性がある。
定義更新経路、クラウド保護、自動サンプル送信は施設ポリシーで管理する。検査合格は無害の保証ではない。

## 記録と障害時

作業領域は `%LOCALAPPDATA%/MedicalDiscImporter/Quarantine/<処理ID>/`。
現在ユーザー・SYSTEM・Administratorsに限定したACLを作成し、コピー、ISO、manifest.json、verification.json、scan.json、job.jsonを保持する。
scan.jsonは判定理由、定義版、Scan ID、開始・完了イベントのRecord ID、終了コードを記録する。
患者名・シーケンスやコマンドの生出力は通常ログに保存しない。manifestの元パス、患者ID、出力名は患者情報を含み得るためアクセス権・保持期限を管理する。

失敗・中止でも作業領域を自動削除しない。出力先の `.partial` ファイル／フォルダも保持する。
最終名への変更は同じ出力フォルダ内で行う。DICOMは一式準備後にフォルダ名を変更する。
ISOとDICOMを一括で原子的に保存することはできない。ISO保存後のDICOM失敗は `PartialOutput` とし、保存済みISOを削除しない。
強制終了・電源断・ネットワーク断では、終了時刻のないjob.json、`.partial`、最終出力を管理者が照合する。
自動再送・再開は未実装。再取り込みは別処理になるため重複に注意する。
共有の空き容量は事前保証できず、コピー失敗時に止める。作業領域はM1の空き容量検査を継続する。

## ビルド・発行

.NET 10 SDKと.NETデスクトップ開発対応Visual Studioを用意し、ソリューションのAppをスタートアップにする。

```powershell
dotnet build MedicalDiscImporter.sln -c Debug -p:Platform=x64
dotnet run --project src/MedicalDiscImporter.App
# ARM64版とx64版をまとめて発行
dotnet publish src/MedicalDiscImporter.App -p:PublishProfile=WinArm64
# x64版のみ発行する場合
dotnet publish src/MedicalDiscImporter.App -p:PublishProfile=WinX64
```

Visual Studioでは `WinArm64` を選んで「発行」すると、ARM64版に続いてx64版も発行する。両方の発行が成功した場合に完了する。`WinX64` はx64版だけを発行する。
出力は `artifacts/publish/win-arm64/MedicalDiscImporter.App.exe` と `artifacts/publish/win-x64/MedicalDiscImporter.App.exe`。各CPU向けにそれぞれ単一EXEを生成する。
ARM64版だけが必要な場合は `dotnet publish src/MedicalDiscImporter.App -p:PublishProfile=WinArm64 -p:PublishX64WithArm64=false` を使用する。
自己完結型単一EXE。ランタイムは実行時に一時展開する。COMのためトリミング・NativeAOTを使わない。
fo-dicomは.NET Standard 2.0のマネージドパーサー（MS-PL）。ネイティブ画像codecは追加しない。
ARM64の発行と実機動作は別に確認する。配布時はライセンス／通知を同梱する。

## 試験

追加テストフレームワーク不要のコンソールランナー。`dotnet test`での検出には非対応。

```powershell
dotnet run --project tests/MedicalDiscImporter.Tests
dotnet run --project tests/MedicalDiscImporter.Tests -- --imapi --mount
# 管理者権限・検査対象に除外なし・最新定義の端末で正常完了の相関を検証
dotnet run --project tests/MedicalDiscImporter.Tests -- --defender
# 通常権限で状態を取得できない端末で出力禁止を検証（上記と別の環境条件）
dotnet run --project tests/MedicalDiscImporter.Tests -- --defender-blocked
# Defender判定の模擬OS応答試験（実スキャン・設定変更なし）
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File tests/MedicalDiscImporter.Tests/DefenderScan.Tests.ps1
# サービス未登録の端末：一般ユーザー所有の偽サービスを拒否する試験
dotnet run --project tests/MedicalDiscImporter.Tests -- --service-spoof
# 管理者がサービスを登録した後、標準ユーザーでダミーDICOMを実検査
dotnet run --project tests/MedicalDiscImporter.Tests -- --service
```

試験成果物は `artifacts/tests/<ID>/` に保持。今回の検証はコンソール74件（実サービス検査・RSB出力の`--service`を含む）とDefender模擬33件、計107件成功。RSBaseの命名・日付別採番・監視側の即時消費・同時出力・外部衝突・中断・採番記録破損と、Defenderの詳細値を検証した。RSBase本体への取込結果、実UNC共有上の監視動作は別途受入試験が必要。
解析・日付代替・ハッシュ一致・出力禁止・衝突・部分成功をダミーDICOMと差し替え検査器で検証する。
`--defender`は無害なダミーDICOMへの実スキャン。正常完了イベント相関を必須とし、未確認を成功扱いしない。脅威を作成したりDefender設定を変更したりしない。

実機受入ではARM64 Surface＋USBドライブで正常、複数日付、日本語名、拡張子なし、破損、中止、抜去、容量不足、共有切断を試す。
管理者が検査ポリシーの検証環境で、検出時の両出力禁止、古い定義・無効状態・イベント取得不能も確認する。
本番利用の前に出力権限・バックアップ・保持期限を決め、管理者によるサービス登録・更新・解除、標準ユーザーの実検査、再起動・サービス停止・中断時の出力禁止を実機確認する。

## 残る制限

再構築ISOは原本のセクタ・トラック・旧セッション・起動情報・音声を保持しない。Windowsから見えるツリーと内容を検証する。忠実なISO/BIN/CUEは未実装。
重複排除、撮影日選択、RSBase内部での取込完了確認、電子カルテ転送、設定の管理者権限分離、自動保持期限・障害後の自動再送は未実装。
IMAPI COMとマウント／解除は即時中断できない場合がある。DICOM解析はタグ境界で中止を確認する。
画面は96 DPIを基準に拡大し、モニターごとのDPI変更に追従する。Windowsの拡大率を150%のまま使用できる。作業領域に収まらない場合はスクロールして操作する。
レイアウト寸法の自動検証は `dotnet run --project tests/MedicalDiscImporter.DpiTests` で実行する。100・125・150・200%相当の起動時寸法と、小さい作業領域でのスクロールを検証する。実モニターの拡大率は変更しない。フォントの実描画、モニター間移動、Surfaceの縦横表示は実機で確認する。
調査根拠と更新記録は [docs/ImplementationPlan.md](docs/ImplementationPlan.md) を参照。
